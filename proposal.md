What this service actually is
runJob() drains up to 10 messages from a Service Bus subscription with a 10s max wait, processes each via handleEvent() (writes an Incidents doc to Cosmos, id: INC-${Date.now()}, source passed through unchanged from the triggering event), then process.exit(0). KEDA's ScaledJob (minReplicaCount: 0) creates a brand-new Kubernetes Job object per scaling decision — there is no persistent Deployment, no Service, no port to forward to. The TriggerAuthentication also runs KEDA's own queue-depth check as create-incident-job-identity-aks via workload identity — so that identity needs Service Bus RBAC beyond what the job container itself needs.

1. Reuses the existing templates as-is, no changes needed
Everything from dependency-scan through rollback-production that doesn't touch the smoke test is genuinely infrastructure-generic already, confirmed by reading the actual job bodies, not assumed:

dependency-scan, sast (plain Node/JS, same as events-service), build-image, container-scan, push-image — none of these care what the built image does at runtime.

The entire promotion template's job orchestration (verify-staging-smoke-test, promote-to-production, smoke-test-production, rollback-production) — none of it inspects what kind of workload it's promoting.
Critically, smoke-test-staging/smoke-test-production's own job bodies (azure/login → install kubectl+kubelogin → get AKS credentials → convert kubeconfig → run ${{ inputs.smoke_test_script_path }} → upload smoke-test-evidence/) are already 100% Deployment-agnostic. Nothing in the template job itself assumes a pod to port-forward to — that assumption lives entirely inside scripts/smoke-test.sh, not in the template.
2. Cannot reuse as-is — needs new, job-specific logic
Only one thing is genuinely incompatible: the smoke test script's content, not its slot in the pipeline. scripts/smoke-test.sh explicitly hard-rejects any SERVICE_NAME besides events-service/incidents-service — and rightly so, because its entire mechanism (ArgoCD-refresh → poll Deployment for expected tag → poll for a Ready pod → port-forward → curl /health → POST/GET) has no equivalent object to target here. Trying to fold a third branch into that script would mean threading a Job-vs-Deployment fork through nearly the whole file, not adding one function — that's a different mechanism, not a variant.

The replacement mechanism, matching the same verification goal (prove the real deployed artifact, using its real Workload Identity, does real work end to end) via a different mechanic:

Confirm ArgoCD sync — same idea as today, different target: poll kubectl get scaledjob create-incident-job -n <ns> -o jsonpath='{.spec.jobTargetRef.template.spec.containers[0].image}' for the expected tag (swap deployment → scaledjob.keda.sh, otherwise identical polling shape).
Publish one synthetic message directly to the real staging/production Service Bus topic+subscription, with a source: ci-smoke-test-<run-id> marker — same correlation-marker convention smoke-test.sh already uses for events-service.
Watch for KEDA to create a new Job object (label-selectable via scaledjob.keda.sh/name=create-incident-job plus a "not seen before this run" timestamp filter) and poll it for .status.succeeded / .status.failed.
Query Cosmos directly (an independent client, same pattern as IncidentsIntegrationFixture.cs) for a document with that source marker in the Incidents container, to prove the write actually landed — the job's own exit 0 only proves the process ran, not that Cosmos accepted the write (a caught-and-swallowed Cosmos error would still completeMessage and exit 0, since handleEvent doesn't catch — actually here it would propagate and dead-letter, but confirming the actual document exists is still the only real proof of the write, same reasoning smoke-test.sh already uses for the other two).
Delete the synthetic Incident (cleanup), write the same evidence-JSON contract to smoke-test-evidence/.
This slots into the existing smoke_test_script_path input (added earlier this session) unchanged — the env var contract (EXPECTED_TAG, NAMESPACE, ARGOCD_APP_NAME, ENVIRONMENT_LABEL, SERVICE_NAME) is already generic enough to carry this.

3. Recommendation: no third template
Reuse service-ci-template.yml and service-promotion-template.yml exactly as they exist today. Point smoke_test_script_path at a new scripts/create-incident-job-smoke-test.sh. This is precisely the scenario that input (and the whole "push differences to the script layer, not the template layer" principle from earlier tonight) was built for — building a third template would duplicate the ~85% of the pipeline (scan/build/push/update-values/rollback) that's already proven identical, just to swap one script call.

Gaps that block building this at all (not workflow decisions — real missing pieces)
No test tooling exists: package.json has zero devDependencies (no jest/eslint/prettier) and "test": "echo \"No tests yet...\"". Per your scoping direction, this needs real unit tests first — mocking @azure/cosmos/@azure/service-bus at the SDK boundary — covering: handleEvent's incident-shape construction, runJob's complete/dead-letter branching and message-loop bounds, azureClients.js's missing-env-var guards.
Integration tests: following this project's own established convention (real Test Service Bus subscription + real InfraMonitorTestDB, not mocks — same pattern events-service/incidents-service already use), verifying a real published message produces the correct real Cosmos write.
Identities: only create-incident-job-identity-aks (runtime) exists. Needs the same three-identity split as the other two services: create-incident-job-ci-identity (Service Bus send/receive + Cosmos RBAC on the test tier, for integration tests), create-incident-job-cd-identity (ACR push), create-incident-job-smoke-identity (AKS/kubectl read + ArgoCD refresh RBAC + Service Bus send on the real staging/production topic + Cosmos read/delete on the real Incidents container for verify+cleanup) — all via Terraform, federated for GH Actions OIDC, least-privilege scoped like the existing ones.
